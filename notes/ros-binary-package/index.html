ROS 2 与 CMake 的二进制包交付

沿着头文件、链接符号和动态加载三个阶段，检查一个 C++ 库能否真正交给另一个工作空间使用。

序言

一段 C++ 代码在作者的机器上能编译运行，并不等于别人已经能用它。使用者拿到的是头文件、一个或多个库文件，以及告诉构建工具如何找到它们的元数据。少其中一种，报错的时刻就会不同。

先分清编译、链接和运行

假设有个库提供一个把温度从摄氏度换成华氏度的函数。头文件告诉编译器函数名、参数和返回类型。库文件里才有编译好的实现。下游源文件包含头文件后，如果编译器能理解那次调用，编译这一关就过了。

可以把整个构建过程按产物写下来：调用方的源文件先变成目标文件，目标文件和库再变成可执行文件，操作系统加载器最后为运行中的程序补齐共享对象。报错发生在这三个产物中的哪一个之前，是判断应找头文件、符号还是动态库的第一条线索。

接下来链接器要为该调用找到对应的已编译符号。当声明正确、实现却没有被链接进来时，常见现象是源码编译成功，链接时出现未定义引用。在 Linux 上，依赖共享库的可执行文件启动时还要经过动态加载器。它会按搜索规则寻找兼容的 .so 文件及其依赖。

这三个阶段各问一个不同的问题。看到“找不到头文件”，先看导出的包含目录。看到 undefined reference，查看实际链接了哪些目标。看到启动时报共享对象打不开，再检查安装位置、运行搜索路径和环境。此时把头文件再复制一份几乎无济于事。

让下游链接一个目标

CMake 包可以导出一个带命名空间的目标。使用者通过 find_package 获取包配置，再让自己的目标链接这个导出目标。库文件的位置、公开头文件目录以及会传递给使用者的依赖由该目标描述，具体机器上的绝对构建路径不应固化到交付接口中。

哪种依赖需要公开，取决于使用者是否见得到它。如果公开头文件的参数就采用另一个库的类型，使用者编译这份头文件时也必须能找到相应声明。若依赖只在实现文件中使用，应按实际链接方式判断运行或链接是否仍需要它。仅凭“作者那边能编译”看不出这些约束。

在 ROS 2 的 ament_cmake 包里，包清单用于描述依赖与工具信息，安装和导出规则则负责把头文件、目标、配置等放进安装目录。开发时叠加一个工作空间可以查到下层包，也可能因此遮住交付缺件。开发机上的搜索路径仍能找到同名旧库，接收者的机器上却只有新装的文件。

用最小消费者验收

准备一个只包含入口程序的小包，调用一个会真正进入共享库的函数。让它仅使用交付的安装目录，编译、链接、运行各做一次。为温度换算选个一眼能验算的输入，0 摄氏度应得到 32 华氏度。只打印“启动成功”的程序不会证明目标符号真能调用。

再把安装目录整体搬到另外一个位置，清空指向原构建树的环境后重复。若仍去旧目录找文件，应查看导出的 CMake 配置和可执行文件里的运行搜索路径。若换了电脑才失败，还要核对 CPU 架构、编译器运行库和 ABI，即两份二进制在符号、类型布局与调用方式上的兼容约定。源码 API 相同不保证这些细节也一致。

换位置后，可用只读工具查看本机可信可执行文件的动态段，例如 readelf -d。NEEDED 记录运行时所需库名，RUNPATH 等字段会影响加载位置。若输出里还出现开发机的旧目录，就能把“在这里启动失败”缩小到一条具体的交付配置。
